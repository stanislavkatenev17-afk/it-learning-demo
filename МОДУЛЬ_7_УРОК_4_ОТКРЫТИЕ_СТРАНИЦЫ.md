## 1. Почему страница не появляется одним действием

Вы вводите адрес сайта библиотеки. Сначала видите заголовок «Часы работы», затем появляется оформление, а чуть позже — фотография входа. Для человека это одно открытие страницы. Для программ за ним стоит несколько разных действий.

Мы уже знаем части URL и смысл HTTP-запроса и ответа. Теперь соберём их в общую цепочку: как программа понимает, куда обратиться, получает материалы и подготавливает показ.

После урока вы сможете по описанию восстановить эту цепочку и объяснить, что уже получено в определённый момент, а о чём пока нет сведений. Отдельно разберём повторное использование материалов и отличие показа от сохранения.

Все истории учебные. Настоящий сайт, действующая сеть, команды, настройки и личный аккаунт не нужны.

## 2. Сначала браузер разбирает адрес

Начнём с простого адреса:

```text
https://library.example/hours
```

Это вымышленный сайт библиотеки. Открывать адрес не требуется. Правила его работы задаёт история урока.

Из предыдущих тем известно:

- `https` — схема обращения по HTTP с защитой соединения;
- `library.example` — имя узла;
- `/hours` — путь к ресурсу, который в нашем примере обозначает страницу часов работы.

Для основной истории зададим условия: страницу открывают через сеть, нужных материалов на устройстве ещё нет, подходящих адресных сведений тоже нет. Не будем переносить эти условия на любое повторное открытие; позже рассмотрим, что может измениться.

Браузер разбирает адрес, чтобы определить способ обращения и цель. Этот шаг ещё не означает получение страницы. Так же чтение имени файла само по себе не загружает его содержание в работающую программу.

```text
Введён URL → определены схема, имя и путь.
Нужные данные страницы ещё не получены.
```

**Проверьте себя.** URL введён и разобран. Доказано ли уже получение расписания?

**Ответ:** нет. Пока определено предполагаемое обращение. Успешное получение содержания — следующий отдельный результат.

## 3. Адресные сведения: задача DNS

Чтобы обратиться к стороне с известным именем, программе нужны адресные сведения.

В модуле 6.6 мы определили DNS — распределённую систему получения сведений, связанных с доменными именами. В наших примерах рассматривается получение IP-адреса по имени.

Браузер и другие средства устройства могут совместно участвовать в этой задаче. Не нужно представлять, что браузер всегда самостоятельно выполняет одну неизменную цепочку обращений ко всем DNS-серверам.

Сначала могут быть использованы ранее полученные пригодные сведения. В основной истории подходящих сведений нет, поэтому требуется их получение. По условию оно успешно:

```text
library.example → получение адресных сведений → подходящий IP-адрес.
```

Указывать числовой IP для этой задачи не требуется. Важен результат: известны адресные сведения для дальнейшего обращения. Сам текст часов работы при этом не предоставлен.

DNS не становится обязательным посредником для всего последующего содержания. Получение адреса и запрос материалов решают разные задачи, как мы уже выяснили в прошлом модуле.

**Проверьте себя.** DNS вернул подходящий IP-адрес для `library.example`. Содержит ли этот результат готовое расписание?

**Ответ:** нет. Получены адресные сведения. За содержанием страницы ещё нужно обратиться к веб-ресурсу и получить соответствующий ответ.

## 4. Связь с нужной стороной

Знание адресных сведений ещё не гарантирует успешного обмена. Нужно, чтобы программы могли передавать данные через нужный сетевой путь.

Вспомним схему из модуля 6: устройство связано с сетью, данные могут проходить через роутер, сеть провайдера и другие сети. Браузер пользуется средствами операционной системы и оборудования. Между окном браузера и серверной программой нет отдельного прямого кабеля только для этого окна.

При `https` используется защита соединения. В нашей основной истории нужная связь с защитой успешно устанавливается до передачи HTTP-содержания. Это отдельно заданный результат, а не вывод только из написанного адреса.

Как проверяется сторона и какие свойства даёт защита, подробно разберём в 7.6. Сейчас достаточно понимать её место в выбранной цепочке.

```text
Есть адресные сведения → устанавливается нужная связь с защитой
→ можно выполнить HTTP-обмен в этой истории.
```

Это смысловая схема. Она не описывает все технические сообщения и не требует нового отдельного соединения для каждого дальнейшего ресурса.

**Проверьте себя.** Можно ли только по факту найденного IP-адреса заключить, что связь с нужной стороной уже успешно установлена?

**Ответ:** нет. Адресные сведения и успешная связь — разные результаты. В основной истории успех связи задан отдельно.

## 5. Запрос и получение основного документа

Теперь браузер может обратиться за страницей часов работы. Вспомним метод из прошлого урока: GET обозначает получение данных ресурса.

Запишем смысл первого обращения:

```text
Действие: GET.
Имя узла: library.example.
Путь: /hours.
```

По условию серверная программа отвечает статусом 200, а браузер полностью получает нужное содержание ответа.

**Основной документ страницы** в нашей учебной модели — материал, с которого начинается её получение и обработка; он содержит описание содержания и может указывать на другие нужные материалы.

Для страницы библиотеки основной документ содержит заголовок «Часы работы», текст расписания и указания на отдельные данные оформления и фотографию входа.

**Материалы страницы, или ресурсы страницы, — данные, используемые при её показе и работе.** К ним относятся основной документ, изображения, описания оформления и, если предусмотрено, программы для действий.

Поэтому основной документ не обязательно содержит всё нужное внутри себя. Например, он может обозначать, какое изображение следует получить отдельно, вместо того чтобы включать данные фотографии в тот же ответ.

Слово «документ» не означает, что на серверном накопителе обязательно лежит готовый файл с тем же именем, что в URL. Способ подготовки ответа определяется серверной программой. Это сохраняет различие пути URL и физического хранения из 7.2.

**Проверьте себя.** Основной документ полностью получен и указывает на отдельную фотографию. Какие данные уже получены и о каком материале нужны отдельные сведения?

**Ответ:** Получен основной документ, включая указание на фотографию. Получение самих данных фотографии нужно установить отдельно. Ссылка на материал и материал — разные данные.

## 6. Почему возникают дополнительные запросы

Обрабатывая основной документ, браузер обнаруживает указания на другие нужные ресурсы. Если нужных данных ещё нет, он обращается за ними.

В нашей истории отдельно нужны описание оформления и изображение входа. По условию каждый материал получается своим GET-запросом:

```text
Браузер → запрос основного документа → ответ с документом.
                   В документе указаны:
                     ├─ описание оформления → свой запрос и ответ;
                     └─ изображение входа   → свой запрос и ответ.
```

Получается несколько запросов, хотя в адресную строку был введён один URL.

Схема показывает зависимости, а не обязательное ожидание каждого предыдущего ответа. Например, после обнаружения двух ресурсов браузер может ожидать ответы на оба обращения в одно время. Не нужно считать, что изображение всегда запрашивается только после полного завершения получения оформления.

В реальных страницах ресурсов может быть больше или меньше. Некоторые материалы уже имеются и могут использоваться повторно. Разные материалы также могут получаться с разных узлов. В основных заданиях всё нужное относится к одному учебному узлу, чтобы не усложнять цепочку раньше времени.

Программы, полученные для страницы, тоже могут обращаться за дополнительными данными. Названия технологий и их роли подробно объясним в 7.5. Для текущей основной истории такие программы не предусмотрены.

**Проверьте себя.** В адресной строке введён один URL, а основной документ указывает на другие нужные материалы. Объясните, откуда могут появиться дополнительные HTTP-запросы.

**Ответ:** Браузер при необходимости обращается отдельно за материалами, указанными в документе. Поэтому один введённый URL не задаёт число запросов за всеми ресурсами. При затруднении отделите основной документ от связанных материалов.

## 7. Обработка и постепенный показ

Полученные данные нужно использовать, чтобы подготовить видимую страницу.

**Обработка и показ страницы — работа браузера с данными, чтобы представить текст, изображения и элементы для действий.** Это не обязательно получение одного готового снимка чужого экрана.

Например, браузер использует описание содержания, правила оформления и изображение. По этим данным он подготавливает расположение и вид частей страницы на вашем устройстве.

**Постепенный показ — появление частей страницы по мере получения и обработки необходимых данных.** В нашей истории текст становится виден раньше фотографии, потому что данные изображения ещё ожидаются.

```text
Момент 1: получен документ, началась его обработка.
Момент 2: есть документ и оформление, текст уже показан.
Момент 3: получение изображения ещё не завершено.
```

Эти подписи описывают конкретную историю, а не одинаковый порядок для всех страниц. В зависимости от материалов и работы программы видимые изменения могут происходить иначе.

Главный вывод: появление текста не подтверждает, что получено всё необходимое. И отсутствие картинки в определённый момент не доказывает её окончательную потерю.

Чтобы говорить о завершении, нужно уточнять: завершено какое действие и какие данные уже есть? Получить основной документ, получить изображение и показать изображение — разные результаты.

**Проверьте себя.** Заголовок уже виден, а данные фотографии ещё ожидаются. Можно ли объявить страницу полностью полученной или фотографию безвозвратно потерянной?

**Ответ:** нет в обоих случаях. По условию есть частичный видимый результат; получение фотографии пока не завершено. Её будущая судьба не установлена.

## 8. Что меняется при повторном обращении: веб-кеш

Ранее мы задали отсутствие нужных данных на устройстве. При повторном использовании это условие может измениться.

Из 6.6 известно слово **кеш**: сохранённые результаты, которые можно использовать повторно. Тогда мы рассматривали адресные сведения DNS.

**Веб-кеш — сохранённые для повторного использования копии полученных веб-материалов.** Здесь рассматриваем такие материалы, доступные браузеру на устройстве пользователя.

Например, ранее полученное изображение может использоваться повторно. Но одной записи копии недостаточно для вывода, что её можно применять всегда. Действуют правила: иногда материал допускается использовать сразу, иногда нужно обратиться к серверу, чтобы проверить пригодность ранее полученного содержания или получить новое.

Мы не изучаем технические поля, управляющие этими правилами. Для решения заданий наличие данных и возможность их повторного использования должны быть заданы явно.

Сравним два разных набора сохранённых сведений:

| Что имеется | Что помогает сделать | Чего не заменяет |
|---|---|---|
| Кеш DNS | Повторно использовать адресные сведения по имени | Данные текста и изображений |
| Веб-кеш | Повторно использовать ранее полученные материалы по правилам | Любые отсутствующие ресурсы или гарантированно самую новую версию |

```text
Нужен материал страницы.
  ├─ есть подходящая копия, правила разрешают использовать её сразу
  │    → можно использовать имеющиеся данные;
  └─ подходящей копии нет или требуется проверка
       → может понадобиться сетевое обращение.
```

Следовательно, каждый показ нельзя рисовать как обязательное полное скачивание всего с нуля. Новый внешний DNS-поиск также не обязателен, если адресные сведения уже доступны и пригодны.

**Проверьте себя.** Для имени есть пригодные сведения в кеше DNS, но изображение никогда не получали. Назовите содержание каждого из двух видов кеша и объясните, чего сейчас не хватает для изображения.

**Ответ:** Кеш DNS содержит адресные сведения, веб-кеш может содержать полученные материалы. Для изображения нужны его данные; адрес их не заменяет, а по условию изображение ранее не получали.

## 9. Показ, работа без сети и отдельное сохранение

Из модуля 6.7 мы знаем два условия для работы без сети: нужные данные должны иметься на устройстве, а программа должна поддерживать соответствующее действие с ними.

Поэтому одного удачного открытия страницы недостаточно, чтобы обещать полную работу без сети в будущем. Часть ресурсов может отсутствовать, некоторые действия могут требовать обращения к сервису, а подходящие копии могут перестать быть доступны для повторного использования.

Наличие веб-кеша также не равно независимой запасной копии. Кеш предназначен для повторного использования по правилам программы, а не для обещания восстановления данных после любой потери.

Отдельно различим сохранение по действию пользователя. Пользователь может специально попросить сохранить материал; результат и полноту такой записи нужно проверить. Подробную инструкцию для конкретного браузера мы сейчас не выполняем.

```text
Показ в браузере → подтверждает определённый видимый результат.
Веб-кеш → может содержать материалы для повторного использования.
Отдельная сохранённая копия → результат отдельного действия и его записи.
```

Из появления страницы также не следует, что записана последняя правка заметки на удалённой стороне. В 6.7 мы требовали подтверждения именно этой записи; смена темы на браузер не отменяет различия.

**Проверьте себя.** На экране виден заголовок страницы. Достаточно ли этого для обещания полной страницы без сети и для подтверждения отдельного сохранённого файла?

**Ответ:** нет. Нужно знать, какие данные действительно имеются, что может программа и какое сохранение выполнялось. Один видимый элемент не подтверждает ни полноту материалов, ни отдельную запись.

## 10. Проверим весь урок

1. DNS успешно вернул адресные сведения. Что ещё нужно для получения и показа страницы?
2. Основной документ полностью получен, но указанные им данные изображения ещё не пришли. Получены ли все материалы и что можно сказать о будущем изображения?
3. Обязательно ли при повторном показе снова получать все материалы через сеть? Что нужно знать о веб-кеше?
4. В кеше DNS есть подходящие адресные сведения. Достаточно ли этого, чтобы прочитать всю страницу без сети?

### Ответы и объяснения

1. **Нужны связь с соответствующей стороной, HTTP-обращение и получение данных, затем их обработка.** При необходимости запрашиваются связанные материалы. Адресные сведения сами не содержат страницу. Повторите части 3–6.
2. **Все материалы ещё не получены; будущий результат для изображения неизвестен.** Указание в документе не заменяет данные изображения, а ожидание не доказывает вечной потери. Повторите части 5–7.
3. **Нет, подходящие материалы могут использоваться повторно.** Важно, есть ли нужные копии и позволяют ли правила использовать их сразу или требуют сетевой проверки. Повторите часть 8.
4. **Нет.** Кеш DNS содержит адресные сведения, а не всё содержание страницы. Для работы без сети нужны данные и поддержка нужного действия программой. Повторите части 8–9 и 6.7.

## 11. Практика по описанию: текст появился, изображение ожидается

**Цель:** восстановить цепочку действий и отделить полученное от неизвестного на промежуточном этапе.

Задание можно выполнить устно, на бумаге или в заметках. Никакие реальные подключения проверять не требуется.

### Условие

Вы открываете `https://library.example/hours`. Подходящих адресных сведений и веб-материалов в кеше нет.

В истории последовательно произошло следующее:

1. DNS-сведения для нужного имени успешно получены.
2. Нужная связь с защитой успешно установлена.
3. Браузер отправил один GET основного документа и получил полный ответ 200 с документом.
4. Документ содержит заголовок «Часы работы», текст расписания и указания на два отдельных ресурса: описание оформления и изображение входа.
5. Браузер отправил по одному GET за каждым из этих двух ресурсов.
6. К моменту **Т** ответ с описанием оформления получен полностью, данные обработаны и текст показан. Ответ с изображением к этому моменту ещё не получен; дальнейшая судьба неизвестна.

Других ресурсов, программ страницы и обращений за материалами нет. Повторных запросов и переходов к другому адресу по указанию сервера не было. Все три ресурса относятся к одному учебному узлу. Число сообщений, потребовавшихся для получения DNS-сведений и установки связи, не задано.

Отдельное сохранение страницы пользователем не выполнялось. О записи полученных материалов в веб-кеш сведений нет.

### Задание

1. Составьте цепочку от разбора адреса до первого показа текста. Назовите имя узла и путь.
2. Подсчитайте только заданные HTTP-запросы за материалами страницы. Следует ли добавлять к ним DNS как ещё один запрос за страницей?
3. Для момента Т укажите, что получено, что ещё не получено и о чём результат неизвестен.
4. Оцените утверждения: «Раз текст виден, получено всё» и «Картинка ещё не пришла, значит потеряна навсегда».
5. Что известно об отдельном сохранении страницы и о записи в веб-кеш?

### Образец результата

Цепочка:

```text
Разбор URL: https, library.example, /hours
→ получение адресных сведений
→ установление связи с защитой
→ GET основного документа → полный ответ 200
→ обработка документа и обнаружение двух ресурсов
→ два GET за оформлением и изображением
→ получение оформления → обработка и показ текста.
```

Всего **три HTTP-запроса за материалами**: один за основным документом, один за оформлением, один за изображением. DNS не является четвёртым запросом за содержанием страницы. Общее число всех сетевых сообщений по этому описанию подсчитать нельзя.

| Что проверяем в момент Т | Результат |
|---|---|
| Адресные сведения | Получены |
| Основной документ | Получен полностью |
| Описание оформления | Получено полностью |
| Текст на странице | Показан |
| Ответ с изображением | Ещё не получен |
| Будущее получение изображения | Неизвестно |
| Отдельное сохранение страницы пользователем | Не выполнялось |
| Запись материалов в веб-кеш | Сведений нет |

Первое утверждение неверно: виден текст, но данные изображения ещё не получены. Второе тоже неверно: промежуточное ожидание не доказывает окончательную потерю.

Отсутствие отдельного сохранения известно из условия. Запись в кеш нельзя ни подтвердить, ни исключить по одному факту показа: этого условия не задают.

### Самопроверка

- URL разобран до обращения; имя узла и путь отделены друг от друга.
- DNS отвечает за адресные сведения, а не выдаёт текст расписания.
- Успех связи указан отдельным этапом.
- Основной документ отделён от двух связанных ресурсов.
- Насчитано ровно три запроса за материалами при данных условиях.
- DNS и служебный обмен не добавлены в этот счёт как материалы страницы.
- В момент Т полученные данные отделены от ожидаемого изображения.
- Не придуманы срок ожидания, окончательный отказ или вечная потеря.
- Отдельное сохранение и неизвестная запись в веб-кеш не смешаны.

Если перепутаны этапы, повторите части 2–6. Если видимый результат оказался доказательством полного получения, повторите часть 7. Если кеш и сохранение получили одну роль, повторите части 8–9.

## 12. Что стоит запомнить и куда идём дальше

При выбранном открытии браузер разбирает URL, получает нужные адресные сведения, устанавливает связь, запрашивает основной документ и при необходимости другие материалы. Затем он обрабатывает данные и подготавливает показ.

Это логическая цепочка. Время получения и обработки может перекрываться, а показ — начинаться до поступления всех материалов. Один адрес не обещает одного запроса.

Кеш DNS помогает повторно использовать адресные сведения. Веб-кеш помогает повторно использовать материалы по правилам. Ни имя, ни адрес, ни один показанный элемент не заменяют полное содержание и не доказывают отдельного сохранения.

В следующем уроке назовём технологии, которыми описывают структуру страницы, её оформление и программные действия: HTML, CSS и JavaScript. Пока мы разобрали назначение материалов обычными словами; новые названия не требовались для выполнения заданий.

## Словарь урока

- **Основной документ страницы** — в учебной модели материал, с которого начинается получение и обработка страницы; содержит описание содержания и может указывать на другие материалы.
- **Материалы, ресурсы страницы** — данные для её показа и работы: основной документ, изображения, описания оформления и программы для действий, если они предусмотрены.
- **Обработка и показ страницы** — работа браузера с данными для представления текста, изображений и элементов для действий.
- **Постепенный показ** — появление частей страницы по мере получения и обработки нужных данных.
- **Кеш** — сохранённые результаты, которые можно использовать повторно.
- **Кеш DNS** — ранее полученные сведения, связанные с именами; в наших примерах используются адресные сведения.
- **Веб-кеш** — копии полученных веб-материалов для повторного использования по правилам.

Логическая схема получения ресурсов соотносится с [MDN — Overview of HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview). Повторное использование ответа и необходимость проверки — [RFC 9111, раздел 4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4). Правила кеша здесь не сведены к обязательному новому скачиванию или вечной пригодности. HTTP-кеш может быть сложнее местных копий в браузере; этот урок сознательно ограничен доступными браузеру материалами на устройстве пользователя. Условия и точное число запросов авторские, настоящая страница не проверялась.

Схема не фиксирует строгую последовательность всех внутренних операций, не предписывает отдельное новое соединение на ресурс и не требует нового внешнего DNS-запроса на каждый показ. Исключение DNS из счёта в практике относится к запросам за материалами страницы; устройство передачи самих DNS-сообщений не разбирается. Три HTTP-запроса следуют только из явно заданного числа ресурсов и отсутствия других обращений.

Названия HTML/CSS/JavaScript даны только в переходе; объяснение ролей остаётся в 7.5. Свойства HTTPS остаются в 7.6. Внутренний конвейер браузера, дерево документа, транспортные протоколы, инструменты разработчика, API и база данных не нужны для ответов. Видео, проверка реальных соединений и проверка на учениках не проводились.
