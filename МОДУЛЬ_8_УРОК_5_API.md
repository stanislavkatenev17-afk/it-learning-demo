## 1. Как другая программа понимает просьбу

Вы нажимаете «Создать» в «Полке». Фронтенд использует значения полей и отправляет обращение бэкенду. Тот проверяет полученное и организует действие с данными.

Но откуда клиент знает, куда обращаться? Как назвать нужное действие, где передать текст и по каким сведениям понять результат?

Для человека есть подписи и кнопки. Программам тоже нужны определённые способы взаимодействия. В этом уроке назовём и разберём их.

После урока вы сможете по небольшому описанию выбрать обращение для получения, создания и обновления заметки, назвать входные данные и объяснить полученный результат. Писать сообщения в техническом формате и отправлять их настоящему сервису не требуется.

## 2. Интерфейс для человека и программный интерфейс

**API, или программный интерфейс, — определённый набор возможностей и правил, по которым программа обращается к другой программе или программной части.** Эти правила задают доступные действия, необходимые данные и возможные результаты.

Запоминать английскую расшифровку не нужно. Важно понять назначение: программа использует предусмотренную возможность через установленный способ обращения.

В форме «Полки» человек вводит название и выбирает кнопку. Клиентская программа на основании этого готовит обращение по правилам API. Одно действие человека может запустить программное взаимодействие, но сама кнопка и API — разные понятия.

```text
Человек → поля и кнопка формы
                     ↓
Клиентская программа → обращение по правилам API → другая программная часть
```

API не обязан быть отдельной страницей, окном или компьютером между участниками. Это способ предоставлять возможности для программного использования.

Например, вместо просьбы «сделайте что-нибудь с заметками» определены конкретные возможности: получить указанную заметку, создать новую или обновить существующую. Для каждой нужны свои сведения.

**Проверьте себя.** API — обязательно ещё одна страница с кнопками, которую должен открыть человек?

**Ответ:** нет. API предназначен для программного взаимодействия. Человек может читать его описание, но обращение по этим правилам выполняет программа.

## 3. Что должно быть известно о действии

**Описание API — сведения о том, как пользоваться его возможностями.** Например, как обозначить нужную заметку и какие результаты возможны.

**Входные данные действия** — сведения, необходимые для его выполнения. **Результат** — сведения о выполнении, отказе или другом установленном состоянии обработки. В нашем сетевом примере данные передаются в запросе, а результат — в ответе.

Возьмём получение заметки с ID 41. Одного имени «Полка» недостаточно. Нужно знать:

- какое действие просит клиент — получение данных;
- какую запись нужно выбрать — ID 41;
- как выразить эту просьбу по правилам сервиса;
- что может прийти в ответ и как это понимать.

Не путайте описание и событие. Наличие записи «можно получить заметку по ID» не означает, что клиент уже обратился и получил данные. Так же известный URL из модуля 7 ещё не был полученной страницей.

API не отменяет проверки бэкенда. Даже правильно составленное обращение может получить отказ, например если действие не разрешено. Описание помогает понять и такой результат.

**Проверьте себя.** Две программы знают имя сервиса, но хотят работать с конкретной заметкой. Назовите ещё три вида сведений, которые задают правила такого обращения.

**Ответ:** Нужны доступное действие, способ выбора заметки и необходимые входные данные. Также важно знать смысл возможного результата. Одно имя сервиса не объясняет правила всех действий.

## 4. Где здесь HTTP и URL

Рассмотрим **сетевой веб-API** — в нашей истории API сервиса, доступный через HTTP-обращения.

Напомним: HTTP задаёт общие правила запросов и ответов, методы и смысл статусов. URL помогает обозначить ресурс. API приложения уточняет, какие возможности доступны, какие ресурсы используются и что означают переданные данные именно в этом сервисе.

Базовый адрес учебной «Полки» — `https://notes.example`. Открывать его не нужно: это условный адрес для объяснения.

В нашем API получение заметки ID 41 описано так:

```text
Метод: GET — получить данные ресурса.
Адрес: https://notes.example/notes/41
Путь: /notes/41 — в этом API выбирает заметку с ID 41.
```

Метод GET знаком из 7.3. Но слово `notes` в пути и выбор ID через `/41` — уже правила учебной «Полки». HTTP не требует, чтобы каждый сервис называл заметки именно так.

Вспомните 7.2: путь URL также не доказывает, что на накопителе есть папка `notes` и файл `41`. Серверная программа определяет, как обработать обозначенный ресурс.

Для названия и текста в следующих обращениях будем использовать условные имена `title` и `text`: **`title` означает название заметки, `text` — её текст**. Это имена данных нашего API, а не универсальные поля HTTP. Писать код с ними не требуется.

**Проверьте себя.** Смысл поля `text` и пути `/notes/41` установлен HTTP одинаково для всех сайтов?

**Ответ:** нет. Их значение задано описанием API нашего сервиса. HTTP предоставляет общие средства обмена, но не назначает эти прикладные названия всем программам.

## 5. Как попросить создание и обновление: POST

Получение данных и просьба изменить их — разные действия. Для новых примеров познакомимся с ещё одним методом HTTP.

**POST — метод, которым клиент просит обработать переданное содержание по правилам выбранного ресурса.** В учебном API «Полки» он используется и для создания, и для обновления заметки. Само слово POST не означает универсальное действие «сохранить» и не гарантирует успеха.

Напомним **тело сообщения**: передаваемое содержание, если оно есть. В наших POST-запросах в теле находятся название и текст. Метод и путь обозначены отдельно.

Для создания клиент ещё не знает ID будущей записи. Он обращается к предусмотренному ресурсу создания. Для обновления уже нужно выбрать существующую заметку.

| Действие | Метод и путь в нашем API | Какие данные передаются |
|---|---|---|
| Получить ID 41 | GET `/notes/41` | ID указан в пути; отдельного тела в этом примере нет |
| Создать новую заметку | POST `/notes` | В теле название `title` и текст `text` |
| Обновить ID 41 | POST `/notes/41/edit` | ID указан в пути; в теле название и текст |

Для другой существующей заметки в этой «Полке» используют её ID в том же месте пути. Например, для ID 61 получение обозначено `/notes/61`, а обновление — `/notes/61/edit`. Это тоже явно заданное правило учебного API, не догадка о любом адресе.

Например, для создания передают «Поездка» и «Билеты». Для обновления ID 41 могут передать название «Встреча» и новый текст «В пятницу». По условиям нашего API второй случай меняет ту же запись, а не создаёт ещё одну.

Это учебное описание смысла, не техническая запись готовых запросов. Реальным программам также нужны сведения о формате содержания. Подробности записи полей и служебных заголовков здесь не требуются.

Пути и использование POST для обновления выбраны для вымышленной «Полки». Другие API могут применять другие пути и методы. Сейчас нужно пользоваться данными правилами, а не выводить их из одного английского слова.

**Проверьте себя.** В учебном API POST используется для создания и обновления. По каким дополнительным сведениям различают эти действия и почему одного слова POST мало?

**Ответ:** Смотрят на выбранный ресурс, путь и правила API. POST просит обработать переданное содержание; конкретное действие определяется правилами ресурса. При затруднении сравните две строки таблицы обращений.

## 6. Успех, создание и принятие в обработку

Из 7.3 знаком **статус HTTP-ответа** — код, сообщающий результат обработки запроса. Разберём три кода в контексте нашего API.

**200** означает успешную обработку. Для чтения в нашей истории с ним приходят данные заметки. Для обновления учебный сервис возвращает с ним подтверждение записи конкретных данных.

**201** означает успешное создание ресурса. В нашем сервисе ответ о создании отправляют после завершённой записи; он содержит присвоенный ID и записанные название и текст.

**202** означает принятие обращения в обработку, которая при формировании такого ответа ещё не завершена. Сам ответ не сообщает её окончательный итог. Дальше действие может быть выполнено или отклонено; без дополнительных сведений выбирать исход нельзя.

| Ответ в учебной истории | Что он устанавливает |
|---|---|
| GET: полный 200 с данными ID 41 | Получены эти данные; новая правка этим чтением не записывается |
| Создание: полный 201 с ID и записанными данными по правилам «Полки» | Подтверждено создание указанной записи с этими данными |
| Обновление: полный 200 с ID и записанными данными по правилам «Полки» | Подтверждено обновление указанной записи этими данными |
| 202 без последующих сведений | Известно принятие в незавершённую обработку, окончательный результат не установлен |

Фраза «после завершённой записи» — важное условие нашего сервиса. Один код сам по себе не описывает физическую долговечность данных, состояние экрана или текст, введённый после отправки.

Для вывода читайте вместе действие, статус, содержание и заданные правила ответа. Получение какого-либо успешного статуса ещё не является одинаковым подтверждением всех действий приложения.

**Проверьте себя.** Клиент получил 202. Сформулируйте подтверждённый результат и сведения, которые ещё нужны для вывода о записанной версии.

**Ответ:** Подтверждено принятие обращения в обработку, которая при формировании ответа ещё не завершена. Для вывода о записи нужен итог именно этого действия с нужными данными. Сам 202 окончательный результат не устанавливает.

## 7. На какой запрос и на какую версию пришёл ответ

Нужно понимать не только смысл ответа, но и его связь с обращением.

**Связь ответа с обращением** позволяет определить, на какой запрос получен результат. В учебном разборе назовём два обращения **Q1** и **Q2**. Это условные метки запросов, не обязательные поля HTTP и не ID заметок.

ID 41 отвечает на вопрос «какая заметка?». Метка Q1 — «какое обращение?». Два обращения могут относиться к одной записи, но передавать разные данные.

Пусть Q1 отправил текст «В среду». Пока ответ ожидался, человек поменял рабочий текст на «В пятницу». В этой истории последующий ввод не меняет уже отправленное содержание Q1, новых обращений до получения ответа нет.

```text
Q1: передан текст «В среду»
             ↓ ожидание ответа
В форме уже «В пятницу», но эта правка ещё не отправлялась
             ↓
Пришёл ответ Q1 о записи «В среду»
```

Такой ответ подтверждает запись «среды», а не всего текущего содержимого формы. Для «пятницы» нужно отдельно проследить соответствующее действие и его результат. В следующем уроке сделаем это подробно.

Если ответ не получен, нельзя только из этого установить отсутствие записи. Она могла завершиться, а сообщение о ней — не дойти. Это различие уже знакомо из 6.7 и 8.3.

**Проверьте себя.** Получен успешный ответ нужного сервиса. Значит ли это, что весь текущий текст формы обязательно сохранён?

**Ответ:** нет. Нужно определить, к какому обращению, записи и данным относится ответ. Подтверждение предыдущей версии не подтверждает последующую правку.

## 8. API бывает и без интернета

До сих пор пример был сетевым: клиент обращался к серверной части сервиса. Но общее понятие API шире такого обмена.

В 5.2 мы рассматривали, как программа пользуется возможностями ОС для работы с файлами. Программа может обратиться к предусмотренному программному интерфейсу ОС, чтобы прочитать местный файл. Взаимодействие при этом не требует отдельного удалённого сервиса.

```text
Сетевой пример:
клиент → веб-API «Полки» → серверная обработка

Местный пример:
программа → API возможностей ОС → работа с местным файлом
```

И там и там нужны определённые возможности и правила использования. Но не везде есть HTTP, веб-адрес или сетевые сообщения.

Поэтому не следует называть API другим именем сайта, URL, базы данных или HTTP. Это понятия с разными назначениями. Веб-API может предоставлять действия с данными базы, но сама база от этого не становится интерфейсом для человека.

**Проверьте себя.** Любой API обязательно требует интернета и обращения к чужому сайту?

**Ответ:** нет. Программный интерфейс может предоставлять ОС или другая программная часть на том же устройстве. Сетевой веб-API — один из вариантов.

## 9. Защищённый обмен и результат действия

В адресе учебной «Полки» указано `https`. Из 7.6 известно: при корректной защите HTTPS обеспечивает свойства защищённого обмена и проверку серверной стороны в рассматриваемой модели.

Но это не решает вместо приложения, разрешено ли действие, допустимы ли данные и завершилась ли запись. Например, сервис может защищённо передать отказ или ответ 202.

Для любого результата полезно последовательно спросить:

1. Какое действие запросили и с какими данными?
2. Какой ответ действительно получен?
3. Что он означает по общим правилам и описанию этого API?
4. К какой записи и версии относится результат?

Если есть только описание API, действие ещё не выполнено. Если есть только отправка, итог ещё не установлен. Если есть подтверждение определённой версии, не переносите его на последующие изменения.

**Проверьте себя.** Данные переданы по исправному HTTPS. Можно ли не выяснять результат API и сразу считать заметку записанной?

**Ответ:** нет. Защита передачи и результат действия — разные сведения. Чтобы утверждать запись, нужен относящийся к ней результат с понятным смыслом и нужными данными.

## 10. Проверим понимание

**Вопрос 1.** Кнопка «Создать» в форме и API — одно и то же? Кто ими пользуется в нашем примере?

**Вопрос 2.** Кто задаёт смысл пути `/notes/41/edit` и полей `title` и `text` в учебной «Полке»?

**Вопрос 3.** Чем отличается полученный 201 с заданным подтверждением записи конкретных данных от ответа 202 без дальнейших сведений?

**Вопрос 4.** API всегда обращается через сеть к сайту? Приведите местный пример из урока.

### Ответы и объяснения

1. **Нет.** Кнопкой пользуется человек, а клиентская программа формирует обращение по правилам API. Один шаг может запускать другой, но средства взаимодействия различаются. Повторите части 2–3.
2. **Правила API этого сервиса.** HTTP задаёт общие средства, а прикладные пути и поля определены для «Полки». В другом API они могут означать другое. Повторите части 4–5.
3. **В первом случае по условиям сервиса подтверждено завершённое создание определённой записи с указанными данными.** Во втором установлено принятие в незавершённую обработку, а окончательный исход неизвестен. Повторите часть 6.
4. **Нет.** Например, программа может использовать API ОС для чтения местного файла без обращения к удалённому сервису. Повторите часть 8.

## 11. Практика по описанию: выбрать обращение и понять ответ

**Цель:** связать действие, метод, путь, входные данные и установленный результат.

Ответьте устно, на бумаге или в удобных заметках. Никаких реальных запросов и аккаунтов не требуется.

### Условие

Используйте учебные правила частей 4–6. Базовый адрес — `https://notes.example`; пути дополняют его. Право на указанные действия есть, других изменений нет. Три истории независимы.

- **А.** Нужно получить заметку ID 41. Клиент отправляет подходящее обращение и полностью получает 200 с названием «Встреча» и прежним текстом «В среду». Никаких изменений в этой истории не отправляли.
- **Б.** Нужно создать заметку с названием «Поездка» и текстом «Билеты». После подходящего обращения клиент полностью получает 201: запись создана, ID 52, название «Поездка», текст «Билеты». По правилам сервиса ответ отправлен после завершённой записи этих данных.
- **В.** Нужно изменить текст существующей ID 41 на «В пятницу», оставив название «Встреча». После подходящего обращения клиент получает только 202. Дальнейшая обработка и её итог неизвестны.

### Задание

Разберите истории по одной. Для каждой подготовьте одну строку с четырьмя колонками: «Метод и путь», «Входные данные», «Полученный ответ», «Установленный результат». Таблицы правил из частей 4–6 можно использовать.

1. Заполните строку А, затем отдельно Б и В. Условия одной истории не переносятся в другую.
2. Сравните полученный ответ и установленный результат в каждой строке.
3. Объясните, почему ответ из А не подтверждает запись «В пятницу».
4. Укажите, каких сведений не хватает для вывода о завершённой записи в В.

### Образец результата

| История | Метод и путь | Входные данные | Полученный ответ | Установленный результат |
|---|---|---|---|---|
| А | GET `/notes/41` | ID 41 указан в пути; отдельного тела в этом примере нет | 200, «Встреча», «В среду» | Получены данные с текстом «В среду» |
| Б | POST `/notes` | В теле: title — «Поездка», text — «Билеты» | 201, ID 52, «Поездка», «Билеты» | Подтверждено создание ID 52 именно с этими данными |
| В | POST `/notes/41/edit` | ID 41 в пути; в теле: title — «Встреча», text — «В пятницу» | Только 202 | Обращение принято в обработку, окончательная запись не установлена |

Ответ А относится к чтению прежних данных в отдельной истории. Он не подтверждает запись «В пятницу». В В нужен результат завершённой обработки, связанный с данным обновлением ID 41 и нужным содержанием. Одного факта ответа, 202 или исправного HTTPS недостаточно.

### Самопроверка

- Метод и путь выбраны по описанию именно этого API.
- Создание в Б не направлено на ID 41, а обновление в В не превратилось в создание второй заметки.
- Действие, путь и значения полей не смешаны.
- В Б присвоенный ID 52 получен как результат, а не придуман заранее клиентом.
- В В принятие в обработку не названо завершённой записью.
- Чтение старого текста из А не подтверждает новую версию и не переносится в другую историю.

При ошибке в обращениях повторите части 4–5, в статусах — часть 6, в связи результата с данными — части 7 и 9.

## 12. Что стоит запомнить и куда идём дальше

API задаёт возможности и правила программного взаимодействия. В сетевом веб-примере HTTP предоставляет общие средства, а описание API уточняет доступные действия, пути, поля и результаты.

Чтобы понять, что произошло, связывайте действие, переданные данные и полученный ответ. Принятие в обработку не равно завершению, а подтверждение одной версии не распространяется на следующую правку. API может работать и местно, без интернета.

В следующем уроке соберём всё вместе: введём новую заметку, отправим её первую версию, изменим рабочий текст во время ожидания и проследим отдельную запись последней правки.

## Словарь урока

- **API, программный интерфейс** — набор возможностей и правил программного взаимодействия.
- **Описание API** — сведения о доступных действиях и способах их использования.
- **Входные данные** — сведения для выполнения действия.
- **Результат** — сведения об установленном состоянии или итоге обработки.
- **Сетевой веб-API** — в примере API сервиса, доступный через HTTP-обращения.
- **POST** — метод HTTP для обработки переданного содержания по правилам выбранного ресурса.
- **201** — статус об успешном создании ресурса.
- **202** — статус о принятии в обработку, которая при формировании ответа ещё не завершена; её окончательный исход он не устанавливает.
- **200** — статус успешной обработки; конкретный результат уточняют по действию и ответу.
- **Метка обращения** — в разборе Q1 или Q2, условное обозначение конкретного запроса, отличное от ID записи.

Общее определение и возможность местного программного взаимодействия сверены по [MDN — API](https://developer.mozilla.org/en-US/docs/Glossary/API). POST — по [RFC 9110, 9.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.3), 201 — по [15.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.2), 202 — по [15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3). Использованы технические значения; учебный API, условия подтверждения и задания авторские.

Условие «после завершённой записи, с ID и записанными данными» относится к вымышленному сервису, а не является дополнительной гарантией любого 200 или 201. POST не объявлен только созданием, 202 — успешной записью. На момент получения 202 дальнейшая работа могла продвинуться; сам ответ её итог не устанавливает. Путь не превращён в физический файл, метки Q1/Q2 — в обязательные поля протокола.

Не изучаются техническая запись тела, JSON, REST, SDK, ключи доступа и инструменты отправки запросов. Выбранный учебный API не означает выбора технологий платформы. Нет требований к написанию кода, настройке оборудования, действующей сети и аккаунтам. Видео, обращения к настоящему сервису и проверка на учениках не проводились.
