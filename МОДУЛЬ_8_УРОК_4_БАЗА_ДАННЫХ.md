## 1. Как найти нужную «Встречу»

В «Полке» уже несколько заметок. Две называются «Встреча», но одна содержит «В среду», а другая — «В пятницу». Вы хотите изменить только первую.

Как приложению различить эти заметки? Где находится их сохранённое содержание? Почему прежняя строка на экране иногда не совпадает с тем, что уже записано?

В прошлом уроке бэкенд проверял обращения и организовывал действия с хранилищем. Теперь подробнее рассмотрим данные: как их можно организовать, найти и изменить.

После урока вы сможете прочитать маленькую учебную таблицу, выбрать записи по явному условию и проследить обновление одной из них. Настоящую базу создавать не нужно: все действия выполняются по описанию, без кода, команд и подключения к сервису.

## 2. Что такое база данных

**База данных — организованный набор связанных данных, с которыми можно работать по определённым правилам: получать, добавлять, изменять и удалять.** В нашем примере это сведения о заметках «Полки».

Слово «организованный» означает, что данные устроены так, чтобы с ними можно было выполнять предусмотренные действия. Например, получить текст выбранной заметки или найти все заметки с указанным названием.

Для первого знакомства будем рассматривать базу через небольшую таблицу. Существуют и другие способы организации баз; наша таблица не описывает их все.

Сохранённые данные и видимый список — разные вещи. На странице могут быть показаны только две заметки из многих, только названия без текста или сведения, полученные раньше. Поэтому база не равна картинке списка на экране.

Также база не является названием ещё одного вида физического устройства. Для хранения и работы нужны реальные носители, память, программы и ОС. В знакомой веб-истории база находится на стороне сервиса; в других приложениях она может находиться и на устройстве пользователя.

**Проверьте себя.** Можно ли считать базой данных только тот список заметок, который сейчас виден на экране?

**Ответ:** нет. Список представляет данные для пользователя и может показывать только часть или прежнее состояние. База — организованные данные, с которыми работает приложение.

## 3. Данные базы и программа управления ими

Сами данные не выполняют инструкции. Чтобы получать и изменять их, нужна программная работа.

**Система управления базой данных, сокращённо СУБД, — программа, которая обеспечивает работу с базой: принимает обращения к данным, организует их получение и изменение.**

База — организованные данные, СУБД — программа для работы с ними. Запоминать длинную расшифровку по буквам не требуется; важнее различать эти роли.

В нашей веб-«Полке» фронтенд обращается к бэкенду. Бэкенд после нужных проверок обращается к СУБД. Та организует действие с базой и возвращает результат. Затем бэкенд может сформировать ответ клиенту.

```text
Фронтенд ── запрос ──→ бэкенд
Фронтенд ←─ ответ ──── бэкенд
                         ↕ обращение к данным и результат
                        СУБД
                         ↕ чтение и изменение
                    база данных
```

Для выполнения этой работы продолжают использоваться ОС, память, накопители и другие средства компьютеров. Схема не означает четыре отдельных устройства или обязательное сетевое соединение на каждой стрелке.

Так же не следует представлять, что каждая заметка обязательно занимает свой отдельный файл. Мы сейчас разбираем организацию сведений для работы приложения, а не размещение каждого байта на накопителе.

**Проверьте себя.** СУБД и текст сохранённой заметки — одно и то же?

**Ответ:** нет. СУБД — программа, а текст заметки — данные. Программа организует действия с этими данными.

## 4. Таблица, запись и поле

**Таблица** в нашей модели — организация данных в строки и столбцы. **Запись** — набор сведений об одном объекте; здесь одна строка соответствует одной заметке. **Поле** — отдельная характеристика записи, например название или текст.

Сначала покажем две характеристики трёх заметок:

| Название | Текст |
|---|---|
| Встреча | В среду |
| Покупки | Чай |
| Встреча | В пятницу |

В первой строке данных находится одна запись: название «Встреча», текст «В среду». Столбец «Название» объединяет значения одной характеристики для разных записей. Верхняя строка с подписями объясняет устройство таблицы; сама она не является ещё одной заметкой.

Слово «поле» встречалось и в форме 8.2. Поле формы — элемент для ввода. Поле записи — характеристика сохранённых данных. Введённое в форму значение можно передать для заполнения поля записи, но ввод и сохранение происходят на разных этапах.

Есть ещё одно различие в слове «запись»:

- «В базе три записи» — речь о трёх наборах сведений, здесь о трёх заметках.
- «Запись данных завершена» — речь об операции сохранения.

Дальше будем уточнять смысл по предложению. Сохранить изменённый текст одной записи не обязательно означает добавить ещё одну запись.

**Проверьте себя.** В верхней строке таблицы написано «Название», ниже — «Встреча», «Покупки», «Встреча». Различите обозначение поля и его значения.

**Ответ:** «Название» обозначает поле. Три нижние надписи — значения этого поля у трёх записей. При затруднении укажите для каждой надписи, описывает ли она столбец или данные одной заметки.

## 5. Как различить заметки с одинаковым названием

По одному названию «Встреча» в нашей таблице нельзя выбрать ровно одну заметку: их две.

**Идентификатор, или ID, — значение, по которому отличают конкретную запись от других.** В учебной таблице каждой заметке назначен собственный номер. Он уникален среди заметок этой таблицы: у двух разных записей не бывает одного и того же номера.

Покажем те же три заметки с их номерами:

| ID | Название | Текст |
|---|---|---|
| 41 | Встреча | В среду |
| 42 | Покупки | Чай |
| 43 | Встреча | В пятницу |

Это три прежние заметки, а не ещё три новых. Мы добавили в объяснение характеристику, по которой их удобно различать.

Просьба «измените заметку с ID 41» указывает на одну запись. Просьба «найдите все заметки с названием “Встреча”» выбирает две.

В нашем примере ID — число. В других системах идентификаторы могут быть устроены иначе. Не нужно приписывать ID 41 единственность во всех сервисах мира или считать, что по нему известны адрес компьютера, расположение файла и текст заметки.

Знание ID также не даёт автоматически права читать или менять запись. Как и в 8.3, право действия — отдельное условие.

**Проверьте себя.** Две заметки называются «Встреча». Выберите обозначение для указания одной конкретной заметки по правилам нашей таблицы и объясните выбор.

**Ответ:** Используем ID: 41 или 43 для нужной заметки. Название совпадает у двух записей и само не выбирает одну. При затруднении найдите признак, уникальный среди заметок таблицы.

## 6. Поиск начинается с условия

**Условие поиска — явно заданное требование к выбираемым данным.** Например: «название в точности равно “Встреча”» или «ID равен 42».

**Выборка — данные, полученные по условию.** Результатом могут быть сведения об одной записи, нескольких или ни об одной.

Для нашей таблицы зададим правило: сравнение названий точное, без поиска по смыслу.

| Условие | Какие записи подходят |
|---|---|
| Название в точности равно «Встреча» | ID 41 и 43 |
| ID равен 42 | ID 42, название «Покупки», текст «Чай» |
| Название в точности равно «Поездка» | Ни одной |

Пустой результат поиска «Поездки» не означает, что вся база пуста. В ней по-прежнему три заметки, но ни одна не удовлетворяет этому условию.

Отдельно сравним два названия: «Встреча» и «Встреча команды». Они похожи по смыслу, но при точном равенстве это разные значения. Мы не добавляем четвёртую заметку в таблицу — только поясняем правило сравнения.

Не нужно угадывать, как ищет настоящий сервис. Он может сравнивать иначе; в наших заданиях способ задан прямо. Получение подходящих данных — работа приложения и средств базы, а не поиск DNS по имени компьютера.

**Проверьте себя.** По правилу «название в точности равно “Встреча”» обязано ли подходить название «Встреча команды»?

**Ответ:** нет. При заданном точном сравнении это другое значение. Похожий смысл сам по себе не выполняет условие равенства.

## 7. Создать новую запись или обновить существующую

**Создание записи — добавление нового набора сведений.** **Обновление записи — изменение уже существующей записи.** В наших примерах для обновления нужную заметку выбирают по её ID.

Рассмотрим два независимых варианта. Каждый начинается с исходных трёх заметок 41–43.

**Вариант создания.** Вы создаёте заметку «Поездка» с текстом «Билеты». По условию ей назначен новый ID 44 и запись успешно завершена. Теперь в таблице четыре заметки; прежние 41–43 остались.

**Вариант обновления.** Вы меняете текст только у ID 41 с «В среду» на «В четверг». Запись изменения успешно завершена. Теперь у ID 41 новый текст, но заметка остаётся той же записью с тем же ID. Число заметок по-прежнему три; ID 43 не изменён.

```text
Создание:
три записи + новая заметка с ID 44 → четыре записи

Обновление, начиная снова с трёх записей:
ID 41: «В среду» → «В четверг»
ID 42 и 43 без изменений → всё ещё три записи
```

Количество зависит от заданного действия. Смена текста не обязана создавать вторую заметку, а одинаковое название не означает обновление прежней: у нового объекта может быть то же название и другой ID.

Здесь ID сохраняется при обновлении потому, что так устроен наш пример. Мы не изучаем все возможные способы организации изменений и истории версий.

**Проверьте себя.** Изменение текста заметки обязательно добавляет новую запись в базу?

**Ответ:** нет. В варианте обновления меняется существующая ID 41, её ID и общее число записей сохраняются. Создание — другое действие.

## 8. Рабочая правка и сохранённая версия записи

Напомним: **рабочая версия — данные, с которыми программа работает сейчас**. **Версия** здесь означает определённое состояние содержания, а не номер выпуска приложения.

Начнём новую отдельную историю с исходной таблицы. В базе у ID 41 записано «В среду». Клиент получил этот текст и показывает его в форме.

Вы меняете текст формы на «В четверг». По условию отправка и запись пока не выполнялись, других изменений в базе нет.

| Где смотрим после местной правки | Текст ID 41 |
|---|---|
| В рабочей форме клиента | В четверг |
| В сохранённой записи базы | В среду |

Затем клиент отправляет запрос обновления именно ID 41 с текстом «В четверг». В этой истории бэкенд получает обращение, успешно выполняет проверки, а СУБД завершает запись изменения. Теперь в базе у ID 41 тоже «В четверг».

Здесь факт сохранения установлен прямо условием о завершённой записи. Если нам известно только о вводе или отправке, этот результат добавлять нельзя. Если нужен вывод о том, что клиент получил подтверждение, доставку такого ответа тоже нужно установить отдельно.

В этой истории нет обязательного поля базы под названием «версия». Мы называем так состояния данных, чтобы различать старый и новый текст. Не нужно добавлять в таблицу технические сведения, которые условие не задаёт.

**Проверьте себя.** Пользователь изменил текст в форме; об отправке и записи сведений нет. Разделите известное состояние формы и неизвестное состояние базы.

**Ответ:** Известно изменение рабочих данных формы. Запись нового текста в базе не установлена. Чтобы сделать вывод о базе, нужно проследить соответствующее действие записи.

## 9. Почему на экране ещё могут быть прежние данные

Продолжим историю с успешно обновлённой ID 41. В базе уже «В четверг».

До обновления приложение также показывало список заметок, полученный раньше. По условию этот список после записи не обновляли. Поэтому в нём может по-прежнему быть строка с текстом «В среду».

Это не противоречие: сохранённые данные уже изменились, а показанный список представляет прежнее состояние. Если программа заново получит нужные данные из обновлённой базы и применит их к списку, он сможет показать новый текст.

```text
Раньше: база ID 41 «В среду» → полученные данные → список «В среду»

Позже: база ID 41 уже «В четверг»
       список не обновлён → всё ещё показывает «В среду»
```

Один экран может содержать и форму с текущим рабочим текстом, и список, который не обновляли. Чтобы понять результат, нужно смотреть, какие данные использует каждая часть, а не требовать мгновенного совпадения всего видимого.

Не обязательно всякий старый текст означает именно эту причину. Здесь отсутствие обновления списка задано прямо. Без условий по одной строке нельзя достоверно определить состояние базы или единственную причину различия.

Так сохраняется правило прежних модулей: показ, получение, рабочее изменение и запись различаются.

**Проверьте себя.** Список показывает старый текст. Доказывает ли это, что запись в базе не изменилась?

**Ответ:** нет. Список может использовать данные, полученные раньше. В нашей истории изменение базы задано как успешно завершённое, а список после него не обновляли.

## 10. Проверим понимание

**Вопрос 1.** Чем база данных отличается от СУБД?

**Вопрос 2.** В таблице две заметки с названием «Встреча». Как указать конкретную из них по правилам примера?

**Вопрос 3.** По условию обновляется только текст существующей ID 41. Обязательно ли меняется её ID или добавляется новая запись?

**Вопрос 4.** Поиск по точному названию «Поездка» дал пустую выборку. Следует ли из этого, что вся база пуста?

### Ответы и объяснения

1. **База — организованные данные, СУБД — программа, обеспечивающая работу с ними.** Данные сами не выполняют инструкции; действия организуют программы с участием ОС и оборудования. Повторите части 2–3.
2. **По ID.** В нашем примере ID 41 и 43 различают две заметки, хотя их названия совпадают. Одно название не выбирает ровно одну из них. Повторите части 4–5.
3. **Нет.** В этом обновлении ID 41 сохраняется, меняется текст той же записи; новая заметка не добавляется. Повторите часть 7.
4. **Нет.** Не найдено подходящих записей, но другие могут существовать. В исходной таблице есть три заметки с иными названиями. Повторите часть 6.

## 11. Практика по описанию: две «Встречи» и одна правка

**Цель:** выбрать записи по условию и проследить изменение одной из них, не смешивая базу с прежним показом.

Ответьте устно, на бумаге или в удобных заметках. Устанавливать СУБД, писать запросы или открывать сервис не нужно.

### Условие

Начинаем с исходной базы, в которой ровно три заметки. Никакое создание ID 44 из поясняющего примера в эту практику не переносится.

| ID | Название | Текст |
|---|---|---|
| 41 | Встреча | В среду |
| 42 | Покупки | Чай |
| 43 | Встреча | В пятницу |

ID уникальны среди этих заметок. Название при поиске сравнивают точно, без поиска по смыслу. Приложение уже получило исходный список и показывает эти данные пользователю.

Бэкенд получает разрешённое обновление только ID 41: текст должен стать «В четверг», название остаётся прежним. СУБД успешно завершает запись. Ни создания, ни удаления заметок, ни других изменений нет.

После завершённой записи выполняются новые обращения за данными прямо к этой обновлённой базе. Ранее показанный список при этом не обновляют. Доставку отдельного подтверждения обновления клиенту условие не задаёт.

### Задание

1. До обновления найдите все ID, у которых название в точности равно «Встреча».
2. Покажите, что находится в базе после обновления: тексты ID 41 и 43, значение ID 42 и общее число заметок.
3. Определите результат точного поиска названия «Поездка» после обновления.
4. Объясните, доказывает ли прежний текст на экране отсутствие записи изменения. Установлено ли, что клиент уже получил подтверждение этой записи?

### Образец результата

До обновления названию «Встреча» соответствуют две записи: ID 41 и ID 43.

После завершённой записи в базе:

| ID | Название | Текст |
|---|---|---|
| 41 | Встреча | В четверг |
| 42 | Покупки | Чай |
| 43 | Встреча | В пятницу |

Заметок по-прежнему три. Обновили только текст ID 41; ID, название и остальные записи не изменились. Новые обращения к этой базе получают соответствующие обновлённые данные. Точный поиск названия «Поездка» даёт пустую выборку, а не пустую базу.

Прежний список на экране всё ещё может показывать «В среду» для ID 41, потому что после изменения его не обновляли. Это не отменяет прямо заданную успешную запись в базе. Но получение клиентом отдельного подтверждения обновления не установлено: условие его не описывает. Факт записи известен нам из описания, а не только из вида экрана.

### Самопроверка

- До обновления найдены обе «Встречи», а не одна первая подходящая строка.
- Изменена только ID 41; текст ID 43 остался «В пятницу».
- ID 42 сохранила название «Покупки» и текст «Чай».
- Не добавлена четвёртая заметка; ID 44 не попала из независимого примера в практику.
- Пустая выборка «Поездки» не названа пустой базой.
- Прежний показ отделён от данных обновлённой базы.
- Завершённая запись не смешана с доставкой подтверждения клиенту.

При ошибке в выборе записи повторите части 5–6, в числе заметок — часть 7, в сохранённом состоянии и показе — части 8–9.

## 12. Что стоит запомнить и куда идём дальше

База данных организует сведения, а СУБД обеспечивает программную работу с ними. В нашей таблице строка — запись о заметке, поля — её характеристики, ID отличает конкретную запись от других.

Поиск зависит от явно заданного условия. Создание добавляет запись, обновление меняет существующую. Рабочая правка, сохранённое состояние и ранее показанная выборка могут различаться; чтобы сделать вывод, нужно знать произошедшие события.

Теперь нам известны основные роли: фронтенд взаимодействует с человеком, бэкенд обрабатывает обращения, СУБД организует работу с данными. В следующем уроке разберём API — программный интерфейс: правила, по которым программы просят друг у друга данные и действия и понимают результаты. Определим его подробно, прежде чем использовать в итоговой истории.

## Словарь урока

- **База данных** — организованный набор связанных данных для предусмотренной работы с ними.
- **СУБД** — система управления базой данных, программа для организации получения и изменения данных базы.
- **Таблица** — организация данных в строки и столбцы в выбранной модели.
- **Запись** — набор сведений об одном объекте; в примере строка о заметке.
- **Поле записи** — отдельная характеристика, например название или текст.
- **ID, идентификатор** — значение, позволяющее отличить конкретную запись от других.
- **Условие поиска** — требование, по которому выбирают данные.
- **Выборка** — данные, полученные по заданному условию.
- **Создание записи** — добавление нового набора сведений.
- **Обновление записи** — изменение уже существующего набора сведений.
- **Рабочая версия** — данные, с которыми программа работает сейчас.
- **Версия данных** — определённое состояние их содержания.

Физическая запись и программная организация данных не противопоставляются: это разные стороны одной работы.

Техническая сверка по официальному учебнику PostgreSQL: [понятия и табличная модель](https://www.postgresql.org/docs/18/tutorial-concepts.html), [столбцы таблицы](https://www.postgresql.org/docs/18/tutorial-table.html), [получение данных по условию](https://www.postgresql.org/docs/18/tutorial-select.html), [обновление существующих строк](https://www.postgresql.org/docs/18/tutorial-update.html). Использованы различия данных и управления, строк и столбцов, выборки и обновления. SQL, примеры источника и требования его установки в урок не перенесены; выбор PostgreSQL для платформы не предлагается. Учебные данные и условия авторские.

В части 7 создание ID 44 и обновление ID 41 — независимые варианты с общим исходным набором из трёх заметок. В частях 8–9 отдельная последовательная история; практика также начинает заново с трёх заметок. Порядок строк не используется как идентификатор. Точный поиск определён до решения, две «Встречи» дают два результата. После обновления меняется только ID 41, строк остаётся три; пустая выборка не означает пустую базу. Прежний список не отменяет факт записи. Доставка отдельного подтверждения клиенту не добавлена.

База не обязана находиться в облаке, состоять из одной таблицы или иметь отдельный файл на каждую запись. СУБД не названа устройством, база — самостоятельно действующей программой, ID — паролем, IP-адресом или универсально уникальным значением. Физические гарантии хранения и независимые запасные копии из одного факта записи не выводятся.

Не изучаются SQL, типы баз, индексы, связи таблиц, транзакции, выдача прав и установка СУБД. Не утверждается, что поиск всегда перебирает все строки по очереди; в модуле 9 можно будет использовать повторение на отдельном учебном примере, объяснив его заново. Поле базы не объявлено переменной программы. Реальных подключений, исполнения команд, настройки устройств, видео и проверки на учениках не было.
